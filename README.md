# Instamart Customer Intelligence & Support Copilot

## Overview

This project builds a data-driven customer intelligence and support copilot for an Instamart-style online grocery platform.

It analyses customer, product, order, and support ticket data to understand customer behaviour, identify customer segments, predict customer lapse risk, classify support tickets, retrieve relevant policies, and evaluate customer support workflows.

The project is organised into four parts:

- **Part A:** Data audit, cleaning, and SQLite database creation.
- **Part B:** Customer segmentation, lapse prediction, and retention analysis.
- **Part C:** Support ticket classification, privacy protection, and ticket routing.
- **Part D:** Policy retrieval, refund handling, agent scenario evaluation, and checkpointing.

## Reproduce

### Requirements

- Python 3.11+
- pandas
- NumPy
- scikit-learn
- joblib
- SQLite

Install the required Python packages using `requirements.txt`.

### Setup

1. Clone or download this repository.
2. Open the project folder in VS Code.
3. Open a terminal in the repository root.
4. Install dependencies:

```bash
pip install -r requirements.txt
```

5. Generate the project data:

```bash
python generate_data.py
```

6. Clean the raw data:

```bash
python clean_data.py
```

7. Verify the SQLite database:

```bash
python check_db.py
```

8. Run the project scripts from the repository root:

```bash
python part_a.py
python part_b.py
python part_c.py
python part_d.py
```

Run each script separately and check its output before proceeding to the next step. Some scripts may depend on files generated by earlier steps.

**Important:** Keep `generate_data.py` and `mock_llm.py` unchanged if the assignment requires the supplied files to remain verbatim.

## Part B — Customer Intelligence

### Customer Segmentation

- Calculated Recency, Frequency, and Monetary (RFM) features using completed orders.
- Compared K-Means clustering for K values from 2 to 8 using inertia and silhouette scores.
- Selected K = 4, which achieved the highest silhouette score (0.526) among the tested values.
- Profiled customer segments using average recency, frequency, and monetary value.
- Identified four customer segments:
  - `Regular_Low_Spend` — 436 customers
  - `Premium` — 138 customers
  - `Loyal_Frequent` — 419 customers
  - `At_Risk_Inactive` — 182 customers
- Used Principal Component Analysis (PCA) to visualise customer segments in two dimensions. The first two components explained 85.2% of the variance.
- Saved segmentation results to `outputs/customer_segments.csv`.

### Lapse Prediction

- Used completed-order history to calculate customer features.
- Defined a prediction cutoff date of `2025-09-01`.
- Labelled customers as lapsed if they had no completed orders on or after the cutoff date.
- Identified 1,156 eligible customers: 443 lapsed and 713 not lapsed.
- Used `recency_days`, `frequency`, and `monetary` as model features.
- Split the data into training and testing sets using an 80/20 stratified split.
- Built Logistic Regression and Random Forest classification pipelines.
- Evaluated models using accuracy, precision, recall, F1-score, and ROC-AUC.
- Compared baseline models with models trained using oversampling on the training data only.

#### Model Evaluation

| Logistic Regression | 0.707 | 0.591 | 0.764 | 0.667 | 0.773 |

- Selected the balanced Logistic Regression model based on its recall and ROC-AUC results.

### Premium Retention List

- Generated an illustrative retention list for Premium customers using predicted lapse probabilities.
- Included 138 Premium customers in the retention list.
- Saved the results to `outputs/retention_list.csv`.

### Part B Limitations

Lapse labels use future order activity relative to the prediction cutoff date. The Premium segment labels are based on whole-window RFM data, so the retention list is illustrative and should not be treated as a leakage-free production evaluation.

This component classifies customer support tickets into four categories:

- Billing
- Delivery

It includes privacy protection, retry handling, output validation, token tracking, and ticket routing.

### Zero-shot Error Analysis

The recorded zero-shot confusion table showed that some fraud and technical tickets were incorrectly classified as billing. Few-shot examples improved the classification results in this run.

### Reliability and Token Budget

- Transient model errors are retried, up to three attempts per ticket.
- Invalid model outputs are flagged for human review.
- A 5,000-token budget demonstration was performed.
- The recorded budget demonstration used 5,037 tokens because the implementation checks the accumulated token total before each model call. A permitted call can take the total above the configured budget.
- Empty, long, and invalid-output tickets are routed for human review.

## Part D — RAG and Customer Support Agent

### Policy Retrieval

- Used five policy documents covering delivery, escalation, payment, privacy, and refunds.
- Implemented TF-IDF-based policy retrieval.
- Used chunks of 40 words with 10-word overlap.
- Compared overlapping chunks with non-overlapping chunks using 14 evaluation queries.
- Saved retrieval evaluation results to `outputs/retrieval_evaluation.json`.

### Agent Tools

The intended support-agent workflow includes the following tools:

- `get_order` — retrieve order details.
- `search_policy` — search relevant policy documents.
- `calculate_refund` — calculate refund eligibility and amount.
- `issue_refund` — record an approved refund.
- `escalate_to_human` — route cases requiring human approval.

### Refund Policy Handling

The policy workflow is intended to check order status, delivery time, refund eligibility, and refund amount before deciding the next action.

Expected handling includes:

- Eligible refund requests can proceed to refund processing.
- Ineligible requests are denied.
- High-value refund requests requiring approval are escalated.
- Missing orders are handled without issuing a refund.
- Repeated tool-call scenarios use a safe fallback.
